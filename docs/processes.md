# Managed background processes

Select `builtin/process` explicitly. It takes one flat object with an `action`: `start`, `list`, `status`, `output` or `stop`, one action per call. `start` takes a shell `command` and optionally a `shell` (`bash` by default, or `powershell` to run it like the `powershell` tool), a `label`, a `cwd` relative to the session, `env_refs` and a `timeout` in milliseconds (no deadline when omitted). `status`, `output` and `stop` take the job `id`; `output` also takes `cursor` and `max_bytes`. A missing field is rejected with an example of that action, for example `{"action":"output","id":"<id>"}`. Normalization reads `timeout_ms` as `timeout` and `process_id`, `shell_id` and `bash_id` as `id`; a field another action uses is dropped with a note. Start returns an opaque job ID after the shell spawns, without claiming application readiness. Other actions use this ID, never an OS PID. Process and Bash have separate tool selection and permission rules; `bash` with `run_in_background: true` starts a job through this tool's rules, hooks and approval (see [tools](tools.md)).

Results are text. `start` returns `Started <id> · <label or command>`; `list` returns one `<id> · <state> · <label>: <command>` line per job, or `No background jobs.`; `status` returns that line for one job with its output byte count; `stop` returns `Stopped <id> · <state>`. `output` returns the page as stdout and stderr text in the order produced, then `[next cursor: N]` and the job state, such as `[running]` or `[exited · exit 0]`; pass that cursor to read on. Host data on the result (never sent to the model) carries the job ID and, for `output`, the page position (`cursor` of its first byte, `next`, the job's `total` bytes, `earliestCursor`, `droppedBytes`, `truncated`).

The dashboard server, CLI invocation or ACP connection owns the supervisor. An acknowledged background start survives completion or cancellation of later turns and dashboard browser disconnects. A start cancelled before acknowledgement is stopped. Jobs finish on their own, their deadline, Stop, session deletion or host shutdown. Library hosts inject a `ProcessSupervisor`; they must close it before closing its session store. A persisted agent requires a supervisor bound to that same database; an unbound or wrong-store supervisor is rejected before claiming the session or spawning. Separate connections to the same database are supported. Agents without persistence may use an in-memory supervisor. A library without a supervisor returns `process_unavailable` promptly. Managed starts work on macOS, Linux and Windows; on Windows they run Git Bash like the `bash` tool and fail with `bash_unavailable` when it is missing; a `powershell` start fails with `powershell_unavailable` when PowerShell is missing. Foreground Bash keeps its existing behavior.

States are `starting`, `running`, `stopping`, `exited`, `failed`, `stopped`, `timed_out` and `lost`. Nonzero exits are failed. Stop is idempotent on terminal records. Shutdown performs bounded TERM/KILL cleanup of the owned POSIX process group. When the command leader exits naturally, remaining non-detached group members are killed before reporting terminal state. Detached descendants and OS processes surviving a host crash are outside that guarantee. On Windows each job runs inside a Job Object owned by Raw's job launcher: Stop, a deadline and shutdown end the whole tree at once with a forced kill, and when the leader exits the job kills every process left in it, detached ones included, before the terminal state is reported. Without the launcher (no .NET Framework compiler), Stop runs `taskkill /T` on a live leader, which misses processes whose parent already exited, and a leader that exits on its own leaves its descendants running. Recovery marks dead-host records lost; it never signals or adopts a persisted PID, restarts a command or revives a handler. Output pages too small for the next UTF-8 character fail explicitly rather than returning a cursor that cannot advance.

Limits are eight live jobs per session, 32 per host and 100 retained terminal records per session. Each job retains at most 1 MiB recent UTF-8 output, with stdout/stderr labels. Output pages contain at most 64 KiB. Cursors are absolute byte positions in observed decoded output; responses include the earliest available cursor, next cursor and dropped/truncated information. Old cursors resume at the earliest retained position; byte offsets within a UTF-8 character advance to the next boundary. Separate OS streams have no total ordering guarantee. Live storage and notifications coalesce at 250 ms, with immediate terminal flush. State and bounded logs use the existing private session database and are removed with the session.

Starting reserves a durable ownership record before spawning. Reservation and session deletion admission are fenced by store transactions, independently of model-turn leases. A foreign store cannot delete a session with starting/running/stopping jobs owned by a live host; expiry skips it. Owner-host deletion fences new starts, completes supervised cleanup and then deletes. Failed cleanup retains session/process records and reports failure. Once the owning host is demonstrably dead, recovery marks jobs lost and deletion may proceed subject to the crash limitation above.

Persistence failures stop new admissions and trigger bounded cleanup through the owned child handles. They appear in the process record's error; failed durable settlement makes shutdown fail while ownership rows remain retained. After storage recovers, closing the supervisor again retries the pending terminal writes. Recovery applies the same terminal-record retention cap as normal completion.

## Commands and independent user controls

The dashboard Commands projection combines foreground Bash activity with managed background jobs. It is host-owned, separate from tool panels; terminal foreground rows survive reconnect and nonzero exit is displayed as failure without changing Bash's result semantics. Logs use absolute byte cursors, bounded pages and explicit truncation; terminal control sequences are stripped for display. Only background rows offer Stop; cancel the turn for foreground commands.

A Stop request is an independently persisted service control with its own ID and idempotency key. It does not acquire the session model-turn lease, append model messages or alter panel working state. Dispatch loads the saved agent's selected tools and current policy, executes builtin/process through registry validation, hooks and approval, and records the outcome. A retry returns the existing receipt; reusing a key for another process is rejected. Pending controls lost with their host are interrupted, never silently re-executed. Approval uses the ordinary dashboard permission endpoint with the control ID in operationId. Read-only Commands metadata and foreground logs expose existing host records. Background output reads use the same selected Process registry, hooks and approval with durable service receipts; these reads never execute shell commands. Audit records retain outcome metadata, not duplicate stdout.

CLI and ACP retain the selected Process tool’s list/status/output text results and ordinary Bash text results as their readable fallbacks. They do not claim a dashboard sidebar or a new asynchronous control extension.

Dead-host recovery also settles pending control receipts when another already-running host observes the session. It does not require restarting that observer. Background jobs become `lost` immediately on confirmed host death; model operations and questions remain fenced until the existing session lease expires, then become `interrupted`.
