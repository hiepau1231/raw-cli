# Agent hooks

Hooks run a selected command when Raw reaches a named session, turn, or tool event. An agent selects exact hook IDs in `agents.NAME.hooks.use`, in execution order. Use `agent/name` for a folder beside the selected config (`hooks/name/`) or `local/name` for a folder under `~/.config/raw/hooks/`. Installed package IDs use `pkg/ALIAS/hooks/EXPORT`. Raw loads no hooks when `hooks.use` is absent or empty.

Each folder has `hook.json` and any scripts it owns. A manifest declares `name`, a nonempty `events` array, `command`, optional `args`, and optional `timeout_ms` (default 60000, maximum 600000). Each event item is `{ "name": "PreToolUse", "match": "builtin/bash", "when": { "source": "arguments", "any": "command", "regex": "(^|[;&|()\\n])\\s*rm(\\s|$)" } }`. Tool event `match` is a bounded glob against the canonical tool ID; `when` uses the same RE2 argument filter as `tools.rules`. Both are optional and invalid on non-tool events. Matching happens before process spawn. The command is an executable on PATH or a `./` path contained in the hook folder. `./` arguments resolve inside that folder; other arguments remain literal. No shell expands the command or arguments. The process runs from the session cwd with Raw's environment and OS permissions.

On Windows a bare command is looked up on PATH with PATHEXT (never in the cwd), and a command path runs by its extension: `.js`, `.mjs` and `.cjs` with the Node that runs Raw, `.ps1` with PowerShell, `.sh` with Git Bash, and `.cmd`/`.bat` through cmd.exe with each argument escaped. The portable form is `{"command":"node","args":["./gate.mjs"]}`. Raw starts each hook inside a Windows job, so when the hook exits, times out or is cancelled, every process it started is stopped too, including ones whose parent has already exited.

The initial events are `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop`, and `SessionEnd`. `SessionStart` means a runtime attachment, including resume; `SessionEnd` means that attachment closed, not that stored history was deleted. A tool hook sees built-in, local, MCP, and ACP tool calls through one boundary. The tool payload carries `source`: `"user_action"` when a person ran a declared panel action from the dashboard, otherwise `"model"` (an absent value means `"model"`). `PostToolUse` and `PostToolUseFailure` fire only after a handler ran. Policy-denied, hidden, invalid, or approval-denied calls do not fire tool hooks.

`raw.hook/2` sends one UTF-8 JSON object on stdin. It contains `protocol_version: 2`, `event`, `cwd`, optional agent/session/turn IDs, and an event-specific payload. Tool events carry `tool: { identity, name, source, arguments, effects?, result? }`. For Raw's built-ins, `arguments` are the normalized arguments (for example `path` when the model sent `file_path`); `raw_arguments` is added with the call exactly as the model sent it when the two differ. `when` conditions match the normalized arguments. A tool result's host data, when present, is `tool.result.host`. The command may write nothing to stdout for success, or exactly one JSON object. `UserPromptSubmit` and `PreToolUse` accept `{ "decision": "continue" }` or `{ "decision": "deny", "reason": "..." }`; exit 2 also denies and wins over conflicting JSON. Exit 0 with empty stdout continues. A response may include a short `message` for host display. Other events are notifications and cannot change an already completed result, except that a `Stop` hook may ask the run to continue ([below](#keeping-a-run-going-from-stop)). A message sent from the dashboard while a turn runs fires its own `UserPromptSubmit` when it is delivered at a step boundary, with that message as `input` and the running turn's IDs; a deny or a blocking failure marks only that message `blocked` with the reason, and the turn continues ([sessions](sessions.md#messages-sent-while-a-turn-runs)). Malformed output, nonzero exit other than 2, spawn failure, timeout, or output overflow blocks a gate and only warns on a notification. A continue response never overrides an existing `ask` or `deny` tool rule.

Every executed hook emits a bounded receipt with its ID, event, outcome, elapsed time, and optional message/error code in live output and visible history. Hook input and raw stdout are not logged by default. Hooks do not edit model messages or tool schemas; the one message a hook can cause is the continuation a `Stop` denial adds. Selected hook files are snapshotted at runtime load; editing a source file cannot change an already attached runtime. New bytes take effect on the next attachment/turn, including resume, and meaningful changes may rotate the generated cache key once. A new user operation can run hooks again; recovery never replays a hook from an interrupted operation.

Commands have bounded stdin (64 MiB of request JSON) and stdout/stderr (1 MiB), timeouts and cancellation. Every hook, including observing `PostToolUse`, `Stop`, `SessionStart` and `SessionEnd` hooks, gets its own `timeout_ms`. A selected folder snapshot allows at most 256 regular files and 16 MiB total, and rejects links. Gates use the active turn's abort signal. Only an interruption shortens observing hooks: a hook already running when the run is interrupted keeps at most two more seconds, and the remaining observing hooks share a two-second cleanup window before the durable operation receipt. Raw terminates the hook process tree when these windows expire. A script's own side effects cannot be rolled back. Scripts should make externally visible side effects idempotent if retrying a new user operation is possible.

The command/JSON/event pattern follows common CLI-agent hook designs, but `raw.hook/2` is Raw's own protocol. It is not an implementation of another product's hook API.

## Keeping a run going from `Stop`

A `Stop` hook may answer `{ "decision": "deny", "reason": "..." }` (or `{ "decision": "continue" }`, the default) when the run ended `completed`, meaning the model gave a final answer. Raw then does not stop: it records `[Raw hook continuation] <reason>` as a host message with the user role and makes one more model request. The model sees the prefix and knows the message is not from a person. This is the building block for packages that want goal-like behaviour ("keep working until X"): Raw has no goal feature, and the state, criteria, budget and commands of such a feature live in the package.

- Every `Stop` hook runs, as before. The reasons of all denying hooks are joined with a blank line and cut at 4096 bytes. A `reason` is at most 1024 bytes; an empty one becomes "A Stop hook asked the run to continue."
- Only a `completed` end can be continued. A run that ended in error, was cancelled or hit the tool-step limit ignores the decision, and an interruption while the hooks run ends the run as it would have ended. Exit code 2 does not deny `Stop`; only the JSON answer does.
- A failing, timed-out or invalid `Stop` hook never keeps the run going.
- The request of a `Stop` hook has `run` (`status`, `steps`, `text`) and `stop`: `hook_active` (a `Stop` hook already continued this turn), `continuations` (how many times) and `usage` (the session's cumulative usage summary, not only this run's, so a package that keeps a budget subtracts the value it saw when its goal began). Observing hooks can use `hook_active` to skip the intermediate calls.
- Each continuation is one more model request counted in `steps`. The only bound Raw adds is `maxSteps`: when a denial arrives with no step left the run ends `max_steps` with the message "a Stop hook asked the run to continue", so a host can tell a cut run from a finished one. A hook should stop denying by itself, for example once `stop.continuations` reaches its own limit.
- A package that uses this declares `"requires": ["raw.stop-continue/1"]`. The installed `examples/hooks/keep-going/` denies until a file named `DONE` exists in the working directory, at most three times.

## Runnable examples

The installed `examples/hooks/guard/` contains a Node gate and failure notification. Copy it to `hooks/guard/` beside your selected config, then add `"hooks":{"use":["agent/guard"]}` to the intended agent. Its `PreToolUse` subscription matches `builtin/bash` and uses `command` with RE2 to narrow to direct `rm` commands. The script writes `{"decision":"deny","reason":"Review removal commands first"}`. Its `PostToolUseFailure` subscription writes `{"message":"Bash command failed"}`. The regex is textual and does not parse shell syntax; keep or add tool policy for broader protection.

For a Python notification, create `hooks/notify/hook.json` with `{"protocol_version": 2, "name":"notify","events":[{"name":"Stop"}],"command":"python3","args":["./notify.py"],"timeout_ms":3000}` and `hooks/notify/notify.py`:

```python
import json
import sys

event = json.load(sys.stdin)
print(json.dumps({"message": f"Turn {event.get('turn_id', 'unknown')} finished"}))
```

Select `agent/notify` after any gates in `hooks.use`. The Python script only reports and never asks the run to continue.

For a no-network smoke test, use a config with an available local model or the repository's fake provider fixture. Run `raw --config /path/to/raw.json --agent NAME "Run a harmless printf command"`, then resume the printed session ID with `raw --config /path/to/raw.json --resume ID "Continue"`. A nonmatching `printf` command should have no guard receipt; a matching removal call should show a `hook_denied` result and a `PreToolUse` receipt. Open `raw dashboard`, select the same agent, create a chat and inspect its live hook receipt and saved history. Library → Hooks lets you edit the manifest/script and attach the ID with a revision check; browsing a hook never runs it. `raw --config PATH config list` validates configuration only and does not call the script.

The current development tool inspection contract uses explicit predicate sources and separate intended effects; see [tool-effects.md](tool-effects.md). Old tool/hook formats are not adapted.
